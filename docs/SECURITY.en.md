# Security Policy

## Supported Versions

Only the latest release receives security fixes.

| Version           | Supported          |
| ----------------- | ------------------ |
| Latest release    | :white_check_mark: |
| Previous versions | :x:                |

## Reporting a vulnerability

**Do not open a public issue to report vulnerabilities.**

Use GitHub's [private vulnerability reporting](../../../security/advisories/new) or email [dev@camilaloliveira.com](mailto:dev@camilaloliveira.com), including:

- A detailed description of the vulnerability
- Steps to reproduce
- Expected behavior
- Actual behavior
- Environment (operating system, browser version, etc.)

After you submit the report, the team reviews it and gets in touch to agree on next steps.

## Vulnerability response process

1. **Report confirmation**: we check that the report is valid.
2. **Risk assessment**: we assess the potential impact.
3. **Fix development**: we work on a fix.
4. **Responsible disclosure**: we inform the reporter and, where applicable, the community about the vulnerability and the fix.
5. **Fix release**: we ship the fix in an official project update.
6. **Post-release review**: we review the process to improve future responses.

## Disclosure policy

Our goal is to disclose vulnerabilities responsibly in order to protect users. We follow industry best practices so that vulnerabilities are handled safely and effectively.
